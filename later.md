# Ideas for Later

- I expect that most `Op`s will have a small payload because we record them at such a fine modularity.
  However, every once in a while, application authors might prepare some big object outside of the automatically persisted framework and then bring them in at once (consider, e.g., an image being pasted into a document). The corresponding `Op` for such a "create the following large object and insert it into the following container" action would have a large payload. Currently the payload would first have to be serialized to the journal, and when the journal gets flushed, it would again be kind-of re-serialized to the snapshot. It would be better to allow for an (either automatically or manually invoked) zero-copy flushing mode where, for large payloads, flushing uses the serialized structure in the payload directly. Large blobs in the payload of a serialized `Op` can then be declared as memory allocations, and one obtains a pointer to them. This means that the serialization of `Op`s will have to use a custom format so that we can ensure large blobs get serialized directly in the same representation that they will also have in the snapshot. Also this means that after flushing, the memory area used for the journal is now partially occupied by new, smaller allocated memory areas. And this scheme might interfere with atomicity / crash resistance.
- Allow (possibly transactionally) batch modifications that get recorded in one go when the group is done:
    - Add a type `Batch<'_, Backend>` that can be constructed from a reference to a `Backend` and wraps it, together with an in-memory (non-persisted) `Vec` of `Op`s (or maybe their serialized versions to avoid having lots of `Box<dyn Op>`s).
    - Add a trait method `Guard::transform_backend(&mut self, FnOnce<...>) -> impl Guard<...>`.
    - Add a trait method `Guard::start_batch(&mut self) -> ...` with a default implementation that simply calls `self.transform_backend(Batch::new)`.
    - The `Batch` records any `Op`s to its internal (non-persisted) `std::Vec`. When the `Batch` is dropped, it optimizes the sequence of `Op`s in memory and then serializes them to the journal. If writing to the journal can return an error, then maybe we also want to introduce a method `Batch::commit(self) -> Result<...>` that is called by `Drop` in case users don't care about error handling (the drop handler would panic on errors). We'd also probably need a way to call this on the `Guard`.
    - Maybe also introduce a `Transaction` that, in addition to batching, also enforces atomicity.
- Rewrite `{Bool, Char, I32, ...}Guard` to `Guard<Primitive>` if possible.
- Better in-file representation of `PersistedVec`: the most streight-forward representation of a `PersistedVec` in the snapshot would probably mirror how `Vec`s are represented in memory: a contiguous region in memory that grows (and, in the snapshot, also shrinks) when necessary. But this would require exponential growth to keep the amortized cost of `push` constant, and exponential growth means that as much as almost half of the allocated space might be unused. This might be acceptable in memory but not in a file on disk. For storage in files, it might be more appropriate to represent a variably-sized array as a linked list of fixed-size chucks, where all but the last chunk are always fully filled. This would usually make random access slow, but not in our case because we'll have to hold a list of `UniquePointer`s to the chunks _in memory_ anyway, which will allow for fast random acces. We probably want to make the chunk size (in numbers of entries) a (run-time) parameter, defaulted to some number calculated from the size of each entry and a target chunk size in bytes.
- Alternative in-file representation for `PersistedHashMap`: instead of `HashMap<Key, (u32, Value)>` in memory + `swap_remove` on the persisted vec-of-pairs on every removal, use the persisted part of a `PersistedVec<Option<(Key, Value)>>` (or a vector of `(Key, Value)` pairs plus a bitmask of live entries), set removed entries to `None` (or clear their liveness bit) instead of compacting immediately, and only actually move entries around during compactification. Likely needs some coordination between the `PersistedHashMap` implementation and the allocator's compaction routine (compaction would need to know it's allowed to reorder/drop dead slots specifically for this representation, not just relocate byte ranges verbatim).
- A `full_compaction` method that application code can call explicitly (e.g. when the user wants to export the file): flush the journal, compact the memory, then actually delete everything that's been freed, including shortening the journal/file itself rather than just marking space reusable.
- Introduce a semantic versioning into files that tracks both which app versions can read a given file and which kladde-versions can. We'll probably need a `min_version` and an `last_writer_version` for both, not sure yet.
- It might be useful to introduce additional microops that combine typical behavior. For example: `split` (splits an allocation into two; combines `alloc`, `copy`, `resize`) or maybe only `copy_part` (combines only `alloc` and `copy` but leaves the old data in place for the caller to potentially overwrite). Introducing such microops with higher level semantics might enable additional optimizations.
- Figure out how the derived guards for `struct`s and `enum`s can be used ergonomically in application code.
  - For `struct` guards, it might be worth implementing `set_<field>(value)` convenience methods for each field so that one doesn't have to the dance to get a guard for the field and write to it.
  - For `enum` guards: can we support pattern matching somehow?

## Things to check later

- Is the `copy` operation dangerous? It copies serializes pointers, so they're no longer unique. Should we instead introduce `move` and consider any pointers in the old position renedered moot?

## Regarding write-ahead-logging discipline

Memory operations must be recorded in a carefully thought-out order so that even when the application crashes after only some of the operations have been written to the journal no uninitialized memory is reachable.

- Worth turning into an explicit test strategy: for a given multi-microop mutation, truncate the journal at every possible prefix length and assert replay always leaves a valid (possibly stale, possibly slightly leaky) snapshot — same idea SQLite's WAL recovery tests use.
- For cases where it's not (easily) satisfiable: Maybe introduce two additional `Op` variants: `StartAtomic` and `EndAtomic`. If the journal of an opened file has a dangling `StartAtomic`, truncate it from that point. This might require us to hold off triggering a flush until `EndAtomic` is reached.
