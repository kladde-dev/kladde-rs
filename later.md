# Ideas for Later

## Potential major redesigns

- When opening a kladde file, is there a way around either reading the entire file (or at least all of its memory allocations) into memory initially or performing lots of random read access (i.e., lots of `seek`s)? As long as memory can be allocated anywhere, reconstructing a nested structure of data types can require arbitrary jumping around in the file. Thus, when we're almost done with parsing the file and reconstructing the stored data structure, but not quite yet (and thus still have to hold the file itself in memory too), we temporarily have about twice the memory requirements compared to the in-memory representation only.
    - If this is indeed unavoidable, would the following redesign be a good idea: _always_ hold the entire file in memory (possibly broken up in chunks that never split a kladde memory allocation). Use this "mirror" of the file as a kind of arena for the in-memory allocations. For example, a `PersistableVec` would no longer use a `std::vec::Vec` for its in-memory representation. Instead, reading from a `PersistableVec` would immediatly read from the verbatim in-memory mirror of the file. Advantages: no duplicate operations in-memory and in-file, no doubled memory requirements during opening. Disadvantages: not clear how this fits in with journalling; lifetimes reading now also needs access to the backend (but only via shared references, so less constrained, but might still be clumsy).
- **Lazily-loaded segments.** Let application authors partition a `kladde` file into independently loadable _segments_ — self-contained subtrees of the persisted structure, each occupying a disjoint, non-overlapping region of the file. A segment is materialized only when first accessed (and could later be evicted), so opening a file no longer requires reading or reconstructing all of it: peak memory is bounded by the working set rather than by the total size of the stored data. The non-overlap requirement is what lets a segment be loaded, relocated, compacted, and reclaimed independently of the rest. This is a different angle on the peak-memory concern above — rather than making the whole resident file cheaper to hold, it avoids holding most of it at all. Open design questions: how a segment boundary is declared and referenced (presumably a lazy handle that loads its target subtree on first deref); how a reference from one segment into another behaves when the target isn't resident; and how eviction interacts with live `Guard`s, the journal, and per-segment growth/compaction. Segments are an orthogonally concept to capsules and to `PersistableBlob<T>`, but (a subset of) these three might commonly be used in conjunction.
    - The derive macro should maybe lint against fields that have an atypical combination of these three types, e.g., suggest using `Capsult<Segment<T>>` when a struct field has type `Segment<Capsule<T>>`. The lint should also say how it can be suppressed (`#[kladde(allow_atypical_<something>)]`.

## Design constraints

- While I'm focusing on a rust implementation here, I don't want the kladde _file format_ to be tied to rust or "feel" overly rust influenced. It should be possible to implement kladde libraries for other languages that read and write the same files, and the APIs of those libraries should feel idiomatic for other languages as well. Eventually, I'll want to write a technical specification for the file format, consisting of both (1) what's _required_ for kladde files (i.e., how files have to be layed out so that kladde can load them) and (2) what's _allowed_ in kladde files (i.e., what any implementation of kladde has to be able to read).

## Miscellaneous ideas

- I expect that most `Op`s will have a small payload because we record them at such a fine modularity.
  However, every once in a while, application authors might prepare some big object outside of the automatically persisted framework and then bring them in at once (consider, e.g., an image being pasted into a document). The corresponding `Op` for such a "create the following large object and insert it into the following container" action would have a large payload. Currently the payload would first have to be serialized to the journal, and when the journal gets flushed, it would again be kind-of re-serialized to the snapshot. It would be better to allow for an (either automatically or manually invoked) zero-copy flushing mode where, for large payloads, flushing uses the serialized structure in the payload directly. Large blobs in the payload of a serialized `Op` can then be declared as memory allocations, and one obtains a pointer to them. This means that the serialization of `Op`s will have to use a custom format so that we can ensure large blobs get serialized directly in the same representation that they will also have in the snapshot. Also this means that after flushing, the memory area used for the journal is now partially occupied by new, smaller allocated memory areas. And this scheme might interfere with atomicity / crash resistance.
- Allow (possibly transactionally) batch modifications that get recorded in one go when the group is done:
    - Add a type `Batch<'_, Backend>` that can be constructed from a reference to a `Backend` and wraps it, together with an in-memory (non-persisted) `Vec` of `Op`s (or maybe their serialized versions to avoid having lots of `Box<dyn Op>`s).
    - Add a trait method `Guard::transform_backend(&mut self, FnOnce<...>) -> impl Guard<...>`.
    - Add a trait method `Guard::start_batch(&mut self) -> ...` with a default implementation that simply calls `self.transform_backend(Batch::new)`.
    - The `Batch` records any `Op`s to its internal (non-persisted) `std::Vec`. When the `Batch` is dropped, it optimizes the sequence of `Op`s in memory and then serializes them to the journal. If writing to the journal can return an error, then maybe we also want to introduce a method `Batch::commit(self) -> Result<...>` that is called by `Drop` in case users don't care about error handling (the drop handler would panic on errors). We'd also probably need a way to call this on the `Guard`.
    - Maybe also introduce a `Transaction` that, in addition to batching, also enforces atomicity.
- Rewrite `{Bool, Char, I32, ...}Guard` to `Guard<Primitive>` if possible.
- Better in-file representation of `PersistableVec`: the most streight-forward representation of a `PersistableVec` in the snapshot would probably mirror how `Vec`s are represented in memory: a contiguous region in memory that grows (and, in the snapshot, also shrinks) when necessary. But this would require exponential growth to keep the amortized cost of `push` constant, and exponential growth means that as much as almost half of the allocated space might be unused. This might be acceptable in memory but not in a file on disk. For storage in files, it might be more appropriate to represent a variably-sized array as a linked list of fixed-size chucks, where all but the last chunk are always fully filled. This would usually make random access slow, but not in our case because we'll have to hold a list of `UniquePointer`s to the chunks _in memory_ anyway, which will allow for fast random acces. We probably want to make the chunk size (in numbers of entries) a (run-time) parameter, defaulted to some number calculated from the size of each entry and a target chunk size in bytes.
- `PersistableHashMap`'s tombstone-on-remove representation means dead slots only ever get reclaimed by a real compaction pass (not built yet). Two related follow-ups once that exists: (1) compaction will need to know it's allowed to reorder/drop dead slots for this representation specifically, not just relocate byte ranges verbatim -- some coordination between `PersistableHashMap` and the allocator's compaction routine. (2) Before that exists, a cheaper middle ground: maintain an in-memory free-list of tombstoned slot indices, and have `insert` reuse one (a `write`, no `resize`) instead of always appending past capacity -- bounds on-disk growth under sustained insert/remove churn without needing real compaction at all. Not done yet since it's pure optimization, not a correctness requirement.
- A `full_compaction` method that application code can call explicitly (e.g. when the user wants to export the file): flush the journal, compact the memory, then actually delete everything that's been freed, including shortening the journal/file itself rather than just marking space reusable.
- Introduce a semantic versioning into files that tracks both which app versions can read a given file and which kladde-versions can. We'll probably need a `min_version` and an `last_writer_version` for both, not sure yet.
- It might be useful to introduce additional microops that combine typical behavior. For example: `split` (splits an allocation into two; combines `alloc`, `copy`, `resize`) or maybe only `copy_part` (combines only `alloc` and `copy` but leaves the old data in place for the caller to potentially overwrite). Introducing such microops with higher level semantics might enable additional optimizations.
    - Two more combined content ops, both motivated by the crash-safe-ordering comments in `PersistableBlobGuard::persist` and `PersistableVecGuard::remove`:
        - A `resize_uninit` op that is like `resize` but does *not* promise to preserve the `min(old, new)` leading bytes, for when the allocation is about to be fully overwritten anyway. Saves the copy that a relocating grow would otherwise perform.
        - A `splice` op: like `write` but also taking an `old_len`, atomically bundling the `resize`, the content `write`, and the tail `move` in the correct order for a grow or a shrink. This is what would make `PersistableBlob::set` and `PersistableVec::remove` a *single* atomic op — closing the residual torn-journal windows those methods currently document (a mid-shrink out-of-bounds read is already avoided by ordering, but the transient shifted/duplicated state during `remove`'s `copy`, and the grow/shrink windows in `persist`, only fully collapse with one atomic op). It's also the natural primitive for the blob-diffing idea below, and likely useful well beyond the blob.
- Figure out how the derived guards for `enum`s can be used ergonomically in application code.
    - For `struct` guards, it might be worth implementing `set_<field>(value)` convenience methods for each field so that one doesn't have to the dance to get a guard for the field and write to it.
    - For `enum` guards: can we support pattern matching somehow?
- Two `#[derive(Persistable)]` escape hatches, both modeled on `serde`'s equivalents:
    - `#[kladde(persist_with = "path")]` on a field (like `#[serde(with = "module")]`): let a field whose type is *not* `Persistable` (a foreign type, or one wanting a bespoke on-disk representation) delegate to a named module/set of functions supplying that field's `INLINE_SIZE`/`store`/`load`/`describe`/guard, instead of requiring `FieldTy: Persistable`. This is the field-level alternative to wrapping the value in `PersistableBlob<T>` — it lets a foreign type be laid out inline (static offset, real schema) rather than as an opaque owning blob. Would want a matching helper-module convention (analogous to `serde_with`).
    - `#[kladde(bound = "...")]` on the type (like `#[serde(bound = "...")]`): override the auto-added `T: Persistable` bound the derive puts on every type parameter (the `#[derive(Debug)]` heuristic). Needed for the cases that heuristic gets wrong — a `PhantomData<T>`-style parameter that shouldn't require `Persistable` at all, or a field that uses `T` only inside a wrapper needing a *different* bound. Until this exists, such types must hand-write the impl.
- Introduce two kinds of variable-sized integers. Both are represented as normal fixed-sized integers in memory but differently in the file):
    - One type for integers that typically have a small, _statically known range of allowed values_. For those, use the smallest number of bytes (not necessarily powers of 2) that can hold all allowed values. This type could be used for enum variants (maybe not for those marked `#[non_exhaustive]`, not sure), and it might make quite a big difference in containers that contain long lists of small enums since most enums will only need a single byte. And there's likely no or barly any runtime cost because it's just some statically known bit shifts without branching.
    - A second type for integers that may span large ranges but are usually not huge. They are serialized to a dynamically sized sequence of bytes that describes its own length. I think `postcard` uses such a dynamic small integer representation. Use it if it makes sense. Since this type is dynamically sized, it cannot be used in situations where memory layout and offsets have to be calculated statically. But it could be used, e.g., when writing allocation sizes and pointer indices as part of an `Op` to the journal. We should reconsider if this is worth the additional runtime cost.
- A future utility for analyzing a kladde file/backend generically (independent of the application's own types) should be able to detect leaked memory: walk every allocation reachable from a root value using `Persistable`'s own `INLINE_SIZE`/offset structure (the same information the derive macro and container `store`/`load` implementations already use to know a value's shape) to compute the reachable set, then flag anything else live in the allocator as orphaned. This is the intended long-term backstop for the "every `Persistable` impl is trusted, not compiler-checked, not to leak" convention (see `spec.md`) -- since nothing enforces that trust at compile time, a tool that can verify it after the fact is what keeps the convention honest in practice. Note this would need to know how to interpret "owning" types generically (a header pointing at further content) without knowing the concrete type, which the current design doesn't expose uniformly yet (each type's `store`/`load` know their own shape, but nothing describes it externally) -- may need a small amount of reflection-like metadata added to `Persistable` for this to be practical.
- Related, narrower gap `PersistableString` surfaced (see its `store`/`push_str`/`set` implementation): `push_str`/`set` mutate one byte at a time through `PersistableVecGuard::push`/`remove`, which is simple but not O(1) for a whole-value replace. A bulk "replace all content in one write" primitive on `PersistableVec`/`PersistableVecGuard` (skipping the per-element `store` calls when `T` is a plain byte, or more generally writing a whole contiguous span at once) would make `set` cheaper without changing its observable behavior.
- Cheap diffing in `PersistableBlobGuard::persist`. It currently rewrites the whole postcard serialization on every change, but it already caches the last-written bytes, so it could instead write only the smallest changed span — `[common_prefix .. len − common_suffix)` found with a two-pointer scan — plus a tail shift when the length changes (the `substitute`/`splice` op above). Editing one nested field of a large blob would then write little. The payoff depends on the serialization being *positionally stable*, which postcard's LEB128 varints undermine: an integer crossing a varint-width boundary shifts everything after it, and any earlier variable-length field (a `String`/`Vec`) whose length changes shifts its whole tail — so the win is workload-dependent. A fixed-width, positionally-stable encoding would help (but *not* bincode specifically — it lost its maintainers, see `spec.md`'s On-Disk Layout note). This effectively reconstructs, for the escape-hatch type, what a real `Persistable` already does with static field offsets — which is itself the argument for preferring a real `Persistable` type when write size matters, rather than leaning on the blob. Layer it on the crash-safe ordering already in `persist`.
    - If we decide not to do this, remove the field that holds the serialization of the current value and cache only its length instead (because I think that's all that's actually used today).
- Allow introducing custom `Op`s that call back into either the type or the instance (if providing a ref to the instance is possible without changes to the rest of the system). Example use case: an included PNG image is edited, and we can describe the edit exactly (e.g., "draw a black line of width 1 from point X to point Y" or also: "compress this PNG more aggressively / scale it by 50%"). The type could then implement decoding the old PNG blob (if it's not already in memory), apply the edit, and encode it again, when the Op gets replayed.
- When adding pointer type to the schema, maybe also add unsized types (slices `[T]`, `str`). This would allow generic tools to understand data better and inspect more out-of-the-box.
- Should we really support `char` as a primitive type? If so, how are `char`s serialized? Valid unicode scalar values seem to be <= 0x10FFFF, so they'd fit into 3 bytes. How future proof do we expect this restriction to be?
- `Allocator::read` should probably return an `impl Read`. Analogously, `Allocator::write` should either return an `impl Write` or take an `impl Read` as argument. Returning an `impl Write` would simplify the caller's sites but is likely more complicated to implement on the callee's side.


## Regarding write-ahead-logging discipline

Memory operations must be recorded in a carefully thought-out order so that even when the application crashes after only some of the operations have been written to the journal no uninitialized memory is reachable.

- Worth turning into an explicit test strategy: for a given multi-microop mutation, truncate the journal at every possible prefix length and assert replay always leaves a valid (possibly stale, possibly slightly leaky) snapshot — same idea SQLite's WAL recovery tests use.
- For cases where it's not (easily) satisfiable: Maybe introduce two additional `Op` variants: `StartAtomic` and `EndAtomic`. If the journal of an opened file has a dangling `StartAtomic`, truncate it from that point. This might require us to hold off triggering a flush until `EndAtomic` is reached.
- **Open problem: compaction slides are not replay-idempotent.** The recovery story in [journal-semantics.md](journal-semantics.md) rests on re-deriving the flush schedule from the log and re-running it from the start. That is only sound if every action survives being partially applied and then repeated. Compaction steps do not. A `Step` has `to < from`, and its source and destination *overlap* whenever the gap is smaller than the run — `RelocatableHeap::Step`'s own doc comment says so. Concretely, `from = 1000, to = 950, len = 100`: after 70 bytes the destination `950..1020` has overwritten source bytes `1000..1020`, so a re-run from the beginning reads bytes that are already wrong. Read hoisting does not help here, because hoisting resolves the reads the *fold* can see (`Storage` pieces in a piece table), and the heap's own byte moves appear in no piece table.
    - Three ways out, none obviously best: (1) log the in-flight step's source bytes before performing it — bounded by the compaction budget, so the cost is tunable; (2) chunk a step into pieces whose source and destination do not overlap — always possible, at the cost of extra passes over the same bytes; (3) keep a progress marker and treat the heap's internal moves as a separately-recoverable phase that runs after the data writes.
    - **The footgun for future development:** `resize` is currently *not* affected, but only incidentally. `GainGreedyHeap::resize` finds the new home before releasing the old one — there is an explicit comment saying "so the two ranges cannot overlap and the caller's copy is unambiguous" — so `Relocation::Single` never overlaps. The lift's `Relocation::Double` does not either: its `target` is at or above `addr + size`, and the replacement is drawn from above the vacated gap, which holds only because no live allocation can sit *inside* a gap. That second argument is structural and implicit; nothing states non-overlap as an invariant, and nothing tests it. A future placement policy that let a growing allocation extend *downward* into the gap below it, or a lift that reused overlapping space, would silently move `resize` into the same broken class as compaction — with no compile error and no failing test, just corrupted files after a crash. Worth adding a debug assertion that no `Relocation` a heap returns has overlapping ranges, so the day that changes is the day a test fails.

## Allocator

- **Zero-sized allocations are outside `GainGreedyHeap`'s model.** `alloc(id, 0)` (and `resize(id, 0)`) panic with `attempt to subtract with overflow` in `insert_raw`, because the heap keys allocations by address and a zero-extent allocation both collides with whatever sits at the same address and makes `next - (addr + len)` underflow. Found by the differential oracle in `differential.rs`, which now excludes size 0 from its generator. Decide whether to support them (every allocation would need a distinct address anyway, so probably by rounding up to 1) or to reject them explicitly at the `Backend` boundary -- silently overflowing in a debug build and corrupting the gap structure in a release build is the one option that is clearly wrong.

- In `TypeDescriptor`, maybe make `inline_size` a field for all kinds (i.e., turn `TypeDescriptor` into a struct with fields `inline_size` and `kind`). When serializing or fingerprinting, ignore `inline_size` for everything where `kind` is not `Opaque` or maybe `Capsule`. It can be reconstructed recursively when reading serialized type schemas. But we might need the `inline_size` as a cache when doing schema resolution (although, this probably means we only need it then, not for schemas that we don't need to resolve, so we may decide to hold off and annotate the schema with `inline_sizes` once we need them).
- Pointer widths (32- vs 64-bit) are an application-author choice, realized via the concrete `Pointer<W = NonZeroU32>` plus `Persistable<P = Pointer>` / container defaults — see `generic-allocator.md`. (The earlier "pointer types should be associated types of `Allocator`" idea was rejected there: it would infect the whole `Persistable` stack with a backend type parameter and lose inherent pointer methods, and the `MetaData`/`lookup` table already covers the metadata that motivated it.)
- **Segments.** Should the allocator support `Segment`s (regions that restrict the order of memory allocations, so a subtree can be loaded / relocated / reclaimed independently)? Different from `Capsule`s (which refer to types, outside the allocator's concern), segments look like the allocator's responsibility. They add real complexity: when one segment grows you must move allocations of a neighboring segment out of the way (or page/chunk segments up front). Deferred — capsules are more important and can be built independently.
	- One implementation idea: **nested allocators** — the outer allocator allocates a vector of pages for the segment; an inner allocator manages both its own state and its allocations inside those pages. Needs address translation (outer) or page-boundary respect (inner), plus gluing for allocations spanning pages. Advantage: the segment's *bookkeeping* is stored inside the segment, so it loads lazily with the segment. Disadvantage: many segments ⇒ many in-memory allocators (but segments are large, so relative overhead is small).
	- Static safety (open): a pointer minted by an inner (segment) allocator is meaningless to the outer one, and nothing stops passing it to the wrong allocator unless the pointer *carries* its allocator's identity. The two ways to get that at compile time are (a) generativity / brand lifetimes (`GhostCell`-style invariant lifetime tokens tying a pointer to one allocator instance) — sound but viral and painful for application ergonomics, or (b) making the segment part of the pointer's *type* — which multiplies the pointer-parameter cost. Realistically, expect a **runtime** check instead (the pointer's id / high bits encode which segment; the wrong allocator returns `None` from `lookup`), not a compile-time guarantee.


## Incremental compaction

- When to call it: probably from a `JournaledBackend`, when the journal gets flushed (roughly):
    1. replay the journal on the `RelocatableHeap` alone (not on the `Store`); don't clear the journal yet.
    2. simulate incremental compaction on the `RelocatableHeap` and append the compaction steps to the journal.
    3. optimize the journal: e.g., a new allocation that gets moved by compaction should be allocated at the new position directly if reordering doesn't break crash resistance.
    4. replay the journal on the `Store`.
- **Use a tree with cursors, to make the `α ≠ 0` case cheap.** The fragmentation term needs `r_src`, i.e. whether an allocation's immediate neighbours are free, which `neighbours_of` currently answers with *two independent descents* of `allocations`: `range(..addr).next_back()` for the neighbour below and `range(addr+len..).next()` for the one above. At `α = 0` both are skipped (the result is multiplied by zero), so this is purely the `α ≠ 0` cost — and it is paid in the search's inner loop, once per candidate. A cursor removes it because the search has *already descended to the right leaf* by the time it needs the neighbours:
    - **Destination-first**: `MoverTree::highest_fitting(w)` descends to the mover and returns only its key. Since `MoverTree` is keyed by address over *every* allocation, its neighbours in the tree *are* the allocation's neighbours — so if the query returned a cursor instead, `prev`/`next` would be O(1) leaf-chain steps and both `allocations` descents would disappear entirely.
    - **Mover-first**: `resizable_candidate` does `allocations.get(addr)` *plus* the same two range queries — three descents for three adjacent entries. One `lower_bound(addr)` descent plus `peek_prev`/`peek_next` collapses that to one.
    - The same collapse applies outside compaction, and there it is not `α`-gated: `insert_raw`, `remove_raw`, `neighbour_addrs` and `resize` each call `prev_end` + `next_start`, so every foreground `alloc`/`free`/`resize` pays two descents that one cursor would cover.
    - Availability is the catch. `std`'s `BTreeMap`/`BTreeSet` cursors (`lower_bound`/`upper_bound`) are still unstable (`btree_cursors`, rust#107540). `sweep-bptree`'s low-level `BPlusTree` does have them — `get_cursor` works for keys that are absent, and `next_with_value`/`prev` walk the linked leaf chain — but the `BPlusTreeMap` wrapper does not expose them, and that crate looks unmaintained. So this likely waits for either std stabilization or a vendored B+ tree.
- **Reward destination gaps that are an integer multiple of the mover.** The gain-greedy policy of `incremental-compaction.md` treats an exactly fitting gap as a tie-break and splits anything larger. Since the whole system is built to mint many extents at few identical fixed sizes, a gap of size `k·s` is nearly as good as an exact fit: it absorbs the `s`-extent and leaves a `(k−1)·s` remainder that is *itself* an exact fit for the same size class, so no sliver is stranded. Worth scoring explicitly (a divisibility bonus, or a preference for `g mod s == 0` among comparable destinations) rather than leaving it to chance. This is the fixed-size-class analogue of the `β`-smoothing idea that was rejected there — same goal (avoid unusable remainders), but exploiting size-class structure instead of a continuous snugness dial.
