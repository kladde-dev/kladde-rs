# Freeing: recursive reclamation of backed memory

Status: **design, not implemented.** This document expands the *Freeing*
section of `spec.md` into a concrete mechanism. v1 leaks on drop (harmless
against the in-memory mock allocator); this is the design for a real,
file-backed allocator whose space actually needs reclaiming.

## The problem

Every "owning" value holds a `UniquePointer<T>` (a fixed-size region, the
`Box<T>` analog) or a `UniqueArrayPointer<T>` (a variable-capacity run, the
`Box<[T]>` analog) naming a content allocation it owns. Removing, replacing,
or discarding such a value must return that storage to the allocator —
recursively, since the value's own fields/elements may own further
allocations.

Today none of that happens. Concretely:

- `PersistableVec<T>::remove` on a `T` that owns sub-allocations (e.g.
  `PersistableVec<PersistableString>`) drops the element's inline header but
  never frees the string's byte allocation.
- A generic whole-content replace (`set` on a non-`u8` vec — see Step 1 of
  `array-pointer-problems.md`) can't exist yet precisely because it has no
  way to free the previous elements' sub-allocations.
- Overwriting a `PersistableVec`-valued map entry, or dropping the `Kladde`
  root, orphans everything underneath.

We want the deterministic, eager reclamation of C++ destructors / Rust
`Drop`: **when a value's owning pointer is removed, its allocation is freed,
and this cascades into every allocation the value transitively owns.** Not a
garbage collector — reclamation is immediate and its timing is a function of
the mutation, not of a background pass.

## Semantics we are copying

1. **Ownership is a forest.** `UniquePointer`/`UniqueArrayPointer` are
   single-owner (not `Clone`), so the "who owns what" graph is a forest:
   every allocation has exactly one owning pointer. Freeing walks a subtree,
   visiting each allocation exactly once — so there is no double-free to
   guard against, only leaks to avoid.
2. **Recursive drop glue.** Destroying a value destroys its fields/elements
   first (or in some deterministic order), exactly like Rust's compiler-
   generated drop glue or a C++ destructor invoking members' destructors.
3. **Move, don't copy.** Transferring an owning value to a new home
   (`std::mem::replace`, moving a value out of a container into another
   backed slot) re-homes its pointer without freeing; only *dropping* frees.
   This keeps the exactly-one-owner invariant intact across transfers.

## Core mechanism: a free hook driven by the type

Add a reclamation hook to the `Persistable` layer — the write-side analog of
`store`/`load`, generated by `#[derive(Persistable)]` and hand-written for
the containers:

```rust
/// Frees every backed allocation this value owns, recursively. After this
/// returns, the value's own storage and all storage beneath it have been
/// journaled for freeing; the in-memory value is left detached (owns nothing).
fn free_owned<B: Backend>(&mut self, backend: &B, location: Location);
```

- **Scalars / plain-old-data:** no-op (own nothing).
- **Derived `struct`:** call `free_owned` on each field at its static offset —
  the derive macro generates this the same way it generates `store`, walking
  the same field list. (Enums: match the discriminant, free the active
  variant's fields.)
- **`PersistableVec<T>`:** for each *live* element call `elem.free_owned(..)`,
  then `backend.free_array(pointer)`.
- **`PersistableHashMap<K, V>`:** for each *live* slot free `K` and `V`, then
  free the slot array.
- **`PersistableString` / `PersistableBlob`:** delegate to the wrapped
  `PersistableVec<u8>`, whose element (`u8`) owns nothing, so it just frees
  the one byte array.

Because each container drives its own recursion, it is the authority on which
elements are live (see *Partial initialization*, below) — the free walk never
touches a slot the container knows is dead or uninitialized.

### Where it is triggered

`free_owned` needs a `Backend` (see next section), so it is invoked from the
guard at the points where an owning value is logically destroyed:

- `Vec::remove` / whole-content `set`, `HashMap::remove`, an `insert`/field
  `set` that overwrites an existing owning value: free the old value before
  discarding it.
- Whole-tree teardown: dropping the `Kladde` root frees the root's subtree.

### Crash-consistency ordering

Freeing obeys the same rule as every other mutation (`spec.md`, *Crash
Consistency*): **publish the unlink before any free.**

1. Emit the one `Write` that removes the subtree's owning pointer / shrinks
   the length so the subtree is no longer reachable.
2. Then emit `Free` microops for the subtree's allocations, in any order —
   single ownership means nothing outside the subtree points into it, so once
   the root is unlinked the whole subtree is unreachable at once.

Any torn-journal prefix is then valid: stop before (1) and the old tree is
intact; stop during (2) and the new state is correct but a few allocations
are momentarily orphaned — the "stale or slightly leaky, never corrupt"
outcome the ordering discipline already targets. A transient subtree
allocated and freed within one unflushed epoch cancels entirely during
flush optimization (`spec.md`, *Flushing*), costing no file space.

## Why the pointer can't free itself (and what follows)

`UniquePointer` deliberately holds no `Backend` reference (it must stay small
and relocatable), so it *cannot* free from a Rust `Drop` impl — reclamation
always needs a backend passed in. Two consequences:

- Freeing is **guard-driven**, not `Drop`-driven on the bare value.
- A removal that **returns** the owning value (`Vec::remove` → `T`) is a
  *transfer*: the returned `T` still names its allocation, and the caller
  must either re-store it (re-homing the pointer) or hand it back to a guard
  to free. The alternative is a **delete** API that frees eagerly and returns
  only a detached, storage-less snapshot (the in-memory data with its
  pointers cleared). Which of these each container offers is a design choice
  to settle per method; both preserve exactly-one-owner. (Rust's `Vec::remove`
  gets the ergonomic transfer for free because `Box` self-frees on drop — we
  don't, so we must be explicit about it.)

## Partial initialization of `UniqueArrayPointer`

A `UniqueArrayPointer<T>` may hold slots that are **not** valid `T`s. Freeing
must visit only the live ones; interpreting a dead/uninitialized slot as a
`T` and following its "pointers" would free arbitrary indices — corruption,
not just a leak. Two representations produce this:

- **Amortized-growth slack.** With capacity ≥ length, slots `[len, capacity)`
  are uninitialized. Free must stop at `len`.
- **Hashmap tombstones.** Each slot carries a 1-byte liveness tag; a removed
  entry clears its tag, leaving stale `K`/`V` bytes behind. Free must skip
  tag-clear slots.

The unifying requirement: **liveness must be recoverable, and uninitialized
memory must never be read.**

### Solution A — type-owned liveness (recommended for the runtime)

The container already knows its live set: the `len` for a vec, the tags for a
map. `free_owned` iterates exactly those, so partial initialization is
invisible to the format — it is a pure implementation detail of the Rust
container, exactly as `Vec<T>`'s drop glue drops only `[0, len)` and never the
spare capacity.

- **+** No format/schema change; matches Rust/C++ semantics directly.
- **+** The type is the authority on liveness, so tombstones and slack "just
  work" with no per-slot metadata.
- **−** Each container hand-writes its free walk (derive generates the
  struct/enum cases); it is *trusted*, not schema-checked, not to leak — the
  same trust model as `store`/`load`.
- **−** Reclaiming an on-disk subtree requires materializing enough of it to
  walk it (you must load a value to know what it owns). Fine for eager freeing
  at mutation time (the value being removed is already in memory), but there
  is no "free this on-disk subtree without loading it."

### Solution B — schema-level liveness (for language-independent tooling)

A non-Rust reader — a generic GC, or the leak-detection utility sketched in
`later.md` — can't run `free_owned`. To let *it* find and follow owning
pointers, the reserved schema kinds would have to be defined (`descriptor.rs`
already reserves `TAG_POINTER = 132` and `TAG_ARRAY = 131`):

- a **Pointer** kind: "an owning `UniquePointer` to type `X` at this offset,"
  distinct from a **reference** (non-owning pointer, which the free walk must
  *not* follow — so owning vs. borrowing has to be a schema-visible
  distinction);
- an **Array** kind: "a `UniqueArrayPointer` to a run of element type `E`,
  with live count `N`," where `N` is given by a referenced length field.

- **+** A single generic walker reclaims/audits any file with only the schema
  and the root — the language-independent backstop for the "trusted not to
  leak" convention.
- **−** Real format surface area and versioning cost; only pays off once
  cross-language tooling exists.

The two solutions are complementary: **A is the destructor** (deterministic
runtime reclamation), **B is the reflection metadata** (external audit/GC).
Build A first; add B when a concrete tool needs it.

## Does `MaybeUninit` need to be its own schema kind?

Short answer: **no** — and it would not even help.

`MaybeUninit<T>` is the right *Rust* tool for the slack in an
amortized-growth array (the container holds `[T; capacity]`-worth of storage
but only `[0, len)` are initialized). Keep it there, as an implementation
detail of the container. It should **not** surface into the file format,
for two reasons:

1. **A format-level "uninitialized" marker is useless to an external reader.**
   The whole point of a schema is to let a reader interpret bytes; "these
   bytes are uninitialized, don't look" gives a generic GC nothing to act on.
   To know what is live, an external tool needs an *always-valid* signal — a
   length, or a discriminant — never an absence of one. So the useful schema
   primitive is the length-bounded **Array** (visit `[0, N)`), not a
   per-slot "maybe" flag.

2. **Our representations already confine uninitialized memory to a
   length-bounded tail, and express every "optional" slot as an always-valid
   discriminant.** In particular, a hashmap's tombstone slot is not
   uninitialized memory at all — it is an `Option`-shaped **enum**
   (`enum Slot { Dead, Live(K, V) }`, a 1-byte tag that is *always*
   initialized), which the existing/reserved `Enum` kind already describes.
   The only genuinely-uninitialized region is the vec's slack past `len`, and
   a length-bounded Array never describes or reads it.

So the invariant to hold the format to is: **uninitialized bytes appear only
as a contiguous tail beyond an explicit length, never interspersed; every
optional slot uses an always-initialized discriminant rather than raw
uninitialized memory.** Under that invariant, existing kinds (a length-bounded
Array whose element may be an `Option`-like Enum) cover every case, and no
`MaybeUninit` kind is needed. A `MaybeUninit` kind would only become necessary
if we allowed *sparse* uninitialized slots interleaved with live ones — a
shape our representations deliberately avoid, and should keep avoiding.

## Recommendation

1. Add `Persistable::free_owned` (Solution A): derive-generated for structs/
   enums, hand-written for the four containers, invoked by guards at
   removal/overwrite/teardown, ordered publish-then-free. This is the
   destructor mechanism and unblocks the generic vec `set`/`remove`.
2. Keep `MaybeUninit` (and all partial-initialization handling) inside the
   Rust containers; the format stays unaware of it.
3. Defer the schema `Pointer`/`Array` kinds (Solution B) until a
   language-independent GC or leak tool actually needs them; when built, model
   arrays as length-bounded and optional slots as `Option`-like enums, so no
   `MaybeUninit` kind is ever required.

## Open questions

- Per-method policy for removal: **transfer** (return the owning value,
  caller re-homes or frees) vs. **delete** (free eagerly, return a detached
  snapshot). Likely per-container, driven by ergonomics.
- Whether `free_owned` should take `&mut self` and null out pointers as it
  goes (so a double `free_owned` is a safe no-op) or consume the value.
- Interaction with a future `references` (non-owning pointer) type: the free
  walk must follow owning pointers only, which is trivial for Solution A (the
  type knows) but forces the owning/borrowing distinction into the schema for
  Solution B.
